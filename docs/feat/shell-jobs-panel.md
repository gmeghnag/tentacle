# feat/shell-jobs-panel — running background shell jobs in the pill and the dropdown

> **Status:** implementation (awaiting approval) · **Branch:** `feat/shell-jobs-panel` (off `main` `dee9a33`)
> **Type:** feat · **Size:** M · **Blast:** load-bearing · **Suited:** DeepSeek exec (who executes stays the owner's call). The task adds protocol methods and a protocol update (§7 protocol) and carries pod-supplied bytes to the terminal (§7 "a pod is not trusted"), so the post-execution Review is **mandatory fresh-context**: it red-teams M2 (the client as the sanitising gate) and H1 (the relay's one writer for `model.jobs`).

Vocabulary: **job** = a background shell job (`bg-N`, started by `shell{run_in_background:true}`); **child** = a background sub-agent (`sa-N`); **dock** = the pill + dropdown + drawer built by `feat/subagent-panel`; **item** = one row of the dock (a child or a job).

## Context

*— deepseek (tentacle --profile deepseek), 2026-11-10*

**Owner requirement** (`TODO.md:471`, owner 2026-11-10, design agreed by the orchestrator): a running background shell job must appear in the dock like a child — the pill (`· N shell`), a dropdown row (`sh-N`, cut command, `running · 4m 10s`), and Enter opens its output tail. The daemon today signals a job's EXIT only. The agreed design, which this plan implements literally:

- a **display update** carrying the **running-jobs list** (id, cut command, `startedAt`, status), sent **ONLY on job start/exit** — never a stream;
- the elapsed time is computed by the TUI from `startedAt`;
- **output is never streamed live**: read on open, **last N lines, size-bounded**, refreshed **at most 1/s and only while that drawer is open**;
- a pod's command text is **untrusted** (§7): one line, control chars stripped, cell-cut, bounded on the client like every other label;
- it also fixes **`fix/detach-open-items` (9d)** (`TODO.md:475`): `ps` says `1 background job(s) running` ~30 s after the job exited.

**Visual truth:** `.tentacle/tmp/subagent-panel/mockups/v3/b.html` (durable copy `.tentacle/site/mockup-generator/mockups-subagent-panel/v3/b.html`), generated by `.tentacle/site/mockup-generator/gen-v3.ts` — the `SHELL` item `{ id:"sh-3", title:"watch: grep -c '^### Turno' conversazione.md", meta:"running · 4m 10s" }` (`gen-v3.ts:236`), the pill counting `2 agents · 1 shell` (`:241`), the row grammar (`rows`, `:83-104`), the dropdown's key hints (`:105`, `:266`). ## Implementation

*— deepseek (tentacle --profile deepseek), 2026-11-10*

### Load-bearing assumption

**A job's start and its output tail are observable on the SAME `JobController` the daemon already holds and hands to the main agent — so the panel needs no new event from the tool, no second registry and no output tee.**

Proven against the code (all citations on `dee9a33`):

1. **One instance, three holders.** `cli/src/wiring.ts:412` creates `const jobs = options.jobs ?? new BackgroundJobs(env)`; the same object goes into the `Agent` (`wiring.ts:617`, consumed at `agent/src/agent.ts:953` as `toolContext.jobs`) and out of the factory (`wiring.ts:273-283` `workerSessionBuild` → `session-host.ts:944,956` → `hosted-session.ts:453`). The shell tool is the **only** caller of `start` (`packages/tools/src/builtins.ts:293`; a child agent gets no `jobs`, `agent/src/subagent.ts:375-400`), so every `bg-N` in a session passes through that one object.
2. **The daemon can already read the running set** — `hosted-session.ts:1334` computes `session/list`'s `jobs` from `this.jobs?.list().filter((job) => job.status === "running")`. Nothing new is needed to *see* the list.
3. **A START is silent** (that is the gap): `JobController` exposes `start/read/kill/list/onExit/dispose` (`core/src/jobs.ts:37-56`); `BackgroundJobs.start` mints the id, buffers and returns a snapshot (`exec/src/background.ts:90-105`) and fires nothing; only `finish` fires (`:171-181`). Measured: `onExit fired so far: []`.
4. **A non-destructive tail is derivable from retained state**: `StreamBuffer` keeps `buf`/`base`/`cursor` (`exec/src/background.ts:24-50`) and only `readNew` moves `cursor` (`:44-49`). A `tail` that slices `buf` leaves the model's next `shell_output` intact — measured.

Falsified by: any path that starts a job outside the session's registry (none: the tool is the only `start` caller, and a child has no registry), or a buffer that discarded the tail without a flag (it keeps 256 KiB and must report the cut — § Failure modes).

### Design

**One new update (`jobs`), two new methods (`session/job_output`, `session/job_kill`), one seam extended (`JobController`), no version bump.**

**1. The registry tells the daemon (core → exec).**
`JobController` gains a required `onStart(listener)` (mirror of `onExit`) and an optional `tail?`:

```ts
/** A job's output tail, as a bounded read a UI may paint. Never moves `read`'s cursor. */
export interface JobTail {
  readonly job: BackgroundJob;
  // Lines, oldest first, EXACTLY as the processes wrote them: raw, never
  // sanitized. Exec owns line-splitting only (the `tail` rule below); the
  // client is the sanitising gate, because a pod's bytes are untrusted (§7).
  readonly stdout: readonly string[];
  readonly stderr: readonly string[];
  /** True: output older than the retained buffer (or an over-long line) was dropped. */
  readonly truncated: boolean;
}
tail?(id: string, opts?: { readonly lines?: number; readonly maxChars?: number }): JobTail | undefined;
```

`onStart` is **required** (every real registry can say it, and an optional one would silently drop a start = a §8 silent drop); `tail` is **optional** as a declared capability, like `App.onSubagents` — the read RPC answers `{found:false, reason}` when it is absent, a typed refusal and never a guess. `BackgroundJobs` fires `onStart` inside `start`, **after** `this.jobs.set(id, job)` and before it returns (`exec/src/background.ts:96-105`) — so a listener that calls `list()` already sees the job, and the tool's own result still comes back with the id; it implements `tail` as a pure slice of `StreamBuffer.buf` (`:24-50`) — **never** through `readNew` (`:44-49`), which is the model's cursor. The `tail` rule, in this order (M1):

1. take the last `maxChars` of `buf`;
2. **split on `\n`** (never on `\r`);
3. inside each line keep only the text **after its last `\r`** — a terminal overwrites that prefix, so a progress bar collapses to its latest frame instead of merging into one huge line;
4. drop the head partial line **only if at least one complete line remains**; otherwise keep that line's tail end and flag `truncated` — so a job emitting one 1 MB line with no `\n` (or only `\r`) still paints a **non-empty, cut** line instead of an empty drawer;
5. keep the last `lines`; `truncated` also when `maxChars` or the 256 KiB retention cut the head.

An empty line is passed through as `""` (the TUI turns it into `" "`, Design §6); nothing is stripped here — that is the client's job (Design §4, M2).

The listener loop is `try`-wrapped per listener, like `AgentJobs.changed` (`core/src/agent-jobs.ts:584-592`): a throwing sink must never make `shell{run_in_background}` fail (the daemon's own listener does not throw — `publishJobs` reports its own errors). The **19** `JobController` fakes gain `onStart: () => () => {}` — `agent/test/{session,resume,running-note}.test.ts` (2 of them use an object literal), `cli/test/{local-runtime,relay,session-jobs}.test.ts`, `client/test/{agent-exit,clear.e2e,serve-autowake,subagent-panel,subagents,unflushed-exits}.test.ts`, `daemon/test/{clear,history-cut,registry,serve-autowake,session-log,session-reaper,unflushed-exits}.test.ts`, `tui/test/{auto-wake,send-now-app}.test.tsx` (measured: `grep -rn "implements JobController" packages/*/test` = 19). `SessionJobsView` forwards it from the current session (`cli/src/session-jobs.ts:33-51` pattern) and `remoteJobsView` no-ops it (`cli/src/local-runtime.ts:173-195`) — the TUI never uses it (it reads the wire), it is there because the interface says so.

**2. Protocol (additive, no bump).**

- `protocol/src/session.ts`, after the sub-agent block (`:428-514`):
  `JobRowSchema = { id: string(min 1), command: string, startedAt: int(non-negative), status: string }` — lenient, **no bound** (strip schema, §7: the client cuts), `status` a free string like `SubagentRowSchema.state`. `SnapshotResultSchema.jobs: z.array(JobRowSchema).optional()` (an older daemon sends none).
  `JobRow.startedAt` is `Job.startedAt = Date.now()` (`exec/src/background.ts:53`), i.e. the **pod's** wall clock at `start` — **not** the host's injected `now()` that sub-agent rows use (`hosted-session.ts:636-638`). Consequence for tests (L1): a daemon test cannot pin an elapsed duration; assert only relative facts (the field is present, non-zero, and equal to the registry's `startedAt`), and leave every duration assertion to the TUI's own pure tests, where `now` is a parameter.
- `protocol/src/session.ts`: `JobOutputParamsSchema = { sessionId, jobId (64), lines?: int 1..200, maxChars?: int 1..16384 }`;
  `JobOutputResultSchema = { found: boolean, jobId: string, status?: string, exitCode?: int|null, startedAt?: int, command?: string, stdout?: string[], stderr?: string[], truncated?: boolean, reason?: string }`;
  `JobKillParamsSchema = { sessionId, jobId (64) }`, `JobKillResultSchema = { killed: boolean }` — the exact shape of `AgentKill*` (`session.ts:488-499`).
- **`session/job_kill` and "a pod is not trusted" (§7, L2 — the claim the Review must check):** the kill is **laptop-originated** (the user presses `x` then `y` in the local TUI; nothing a pod sends can reach this method — a pod-originated `job_kill` frame would be a pod killing its own processes, which it can already do). It acts **only on the daemon's own registry** (`this.jobs?.kill`, the pod's processes), so it has **no effect on the laptop**: no file, no credential, no session history, no model call. It creates **no lasting approval** (`x`+`y` is a per-press confirm, not a stored allow). It is the same trust shape as `session/agent_kill` (`remote-client.ts:940-950`), one level down. Therefore it needs no laptop-side gate beyond the user's own keypress, and the trust argument is complete without one.
- `protocol/src/updates.ts`: `JobsUpdateSchema = { type: "jobs", jobs: JobRow[] }` — full state, replacing any earlier list (never a delta), documented as "sent only on a job's start or exit; display only; nothing waits on it"; added to the union (`:302-326`) and `UPDATE_CLASS.jobs = "display"` (`:347-379`).
- `protocol/src/methods.ts`: `JobOutput: "session/job_output"`, `JobKill: "session/job_kill"` + their entries in `RequestSchemas` (`:120-166`).
- `bun run schema:export` (regenerates `packages/protocol/schema/protocol.json`).

**No `PROTOCOL_VERSION` bump**, and the reason is checkable per §7: nothing existing changes meaning (fields are added; a strip schema drops them on an inbound parse); the update is `display` (an older client skips it once, `updates.ts:408-416`); the methods are new (an older daemon answers `MethodNotFound`, which the client turns into a typed refusal exactly as `remote-client.ts:940-950` does). A new client on an old daemon therefore shows **today's** screen (pill without `· N shell`, no job rows, `x`/`y` refused with a notice) — a degraded but honest state, no hang.

**3. Daemon (projection + publish + the two methods).**
`packages/daemon/src/jobs-view.ts` (new, mirroring `subagents-view.ts`): `jobRows(jobs: readonly BackgroundJob[]): JobRow[]` — running only, one line and bounded (`wireLine(command, JOB_COMMAND_MAX = 200)`, `daemon/src/mapping.ts:64`), `id` cut to 64 (the rows are **never** capped to 32 — that is the client's bound, so `n` stays true); `jobCount(jobs)` = the running count, exported beside the rows so the frame's `n` has one source (H1); `sameJobs(a, b)` for the frame dedupe. `HostedSession`:

- `private lastJobs: readonly JobRow[] = []` (next to `lastSubagents`, `:404`), and the cut's `jobs` (`hosted-session.ts:236-240`).
- `publishJobs()` — `sameJobs` ⇒ no frame; else `lastJobs = rows; emit({type:"jobs", jobs:[...rows]})` and the same idle `recordCut(null)` rule as `publishSubagents` (`:1260-1275`). **The frame is the authoritative list, and its rows are never capped daemon-side**, so the client can derive nothing wrong from it and the count is true (H1). **No coalescing timer**: only a start or an exit changes the set (an exit that merely changes nothing is deduped), so the owner's "sent ONLY on start/exit" is structural, not throttled. It starts with `if (this.closed) return;` like `kickSubagents` (`:1222-1224`): `close()` disposes the registry (`:2692`), whose kills fire `onExit` — those must not frame a session that is going away.
- subscribe where `onExit` is subscribed (`:622`): `this.jobs?.onStart(() => this.publishJobs())` and the existing `onExit` handler calls `this.publishJobs()` **before** it emits `background_exit` (the list must not lag a death); unsubscribe in `close()` next to `:2691`. No initial publish is needed: a session is built with an EMPTY registry (a `serve` reload starts with no jobs, `docs/feat/daemon-side-persistence.md`), and every later job announces itself through `onStart`.
- the cut: `recordCut` (`:1500-1507`) and `historyReplaced` (`:2586-2595`) carry `jobs: this.lastJobs` beside `subagents`; `snapshotPage`'s first page (`:1466`) carries `...(cursor === undefined ? { jobs: [...cut.jobs] } : {})`. `/clear` keeps jobs (§7 `clear-keeps-jobs`), so the barrier must not lose the list.
- `jobOutput(jobId, opts)` → `this.jobs?.tail?.(jobId, opts)`; absent/undefined ⇒ `{found:false, jobId, reason:"this session cannot show a job's output here"}`. Synchronous, never throws, holds no lock (§7 "Don't serialize the RPC peer" — it must not await a turn; `read`-free by construction, so no cursor race with the model's `shell_output`).
- `jobKill(jobId)` → `{ killed: this.jobs?.kill(jobId) ?? false }` — mirrors `killSubagent` (`:1640-1642`).
- `connection.ts`: two cases beside the two synchronous ones (`:273-281`), with the same comment (they never await a turn).

**4. Client (bounded, routed, tolerant) — and the ONE sanitising gate.**
`packages/client/src/jobs.ts` (new, the `subagents.ts` pattern): `MAX_JOB_ROWS = 32`, `boundJobs(rows)` (slice + `progressText` on `id`/`command`/`status`, command cut to 200), `jobsFromSnapshot(rows)`, `boundJobOutput(result)`.

**`boundJobOutput` is the security boundary (M2)** — the daemon may be a pod, so nothing upstream of this function counts as sanitised:

- **Order matters:** the `stdout`/`stderr` arrays are capped to **≤ 200 entries before mapping** (so a 300-entry array cannot make the mapper do 300 units of work), then each kept line is mapped.
- **Per line:** the **same character class** as `progressText` (`client/mapping.ts:90-94`, `[\u0000-\u001f\u007f-\u009f]` ⇒ one space) — `ESC` and C1 (`\x9b`, `\x1b[2J`) included, so a pod's terminal escape can only ever print as text — **plus** the bidi and invisible format controls (`U+200B-U+200F`, `U+202A-U+202E`, `U+2066-U+2069`), stripped (⇒ nothing), because they can visually reorder a line without being control chars.
- **Cap:** 512 characters per line — this module's own constant, **not** `progressText`'s 200. A tab becomes one space, so the cell measurement the drawer does matches what the terminal would do.
- **The same treatment applies to `command`** in a `JobRow` (via `boundJobs`) and in a `JobOutputResult`, and to `id`/`status` (via `progressText`).
- **Totals:** ≤ 200 lines per stream and ≤ 16 KiB of `maxChars` per read; the daemon bounds sizes too (`jobOutput`'s opts), but that is capacity, not trust.

`remote-client.ts`: `SessionEntry.jobs`, `jobsListeners` + `onSessionJobs` + `jobsOf`, `jobsChanged` (like `:2000-2006`), the update branch beside `:2413`, the snapshot path beside `:2240`, `jobOutput()`/`killJob()` beside `:940` (MethodNotFound ⇒ `{found:false, reason}` / `{killed:false}`); `mapping.ts:284-292` gains `case "jobs":` in the list of updates consumed by their own listeners; `remote-session.ts` gains `onJobs`, `jobOutput`, `killJob` (beside `:459-518`) and `"jobs"` in the two non-turn-scoped ignore lists (`:1440`, `:1536`); no index change (`packages/client/src/index.ts:7-17` does not export `subagents.ts` either — `remote-client.ts` imports it directly).

**5. cli (the relay's 9d) — H1: one quantity, one writer.**
Measured: `model.jobs` today means **shells + children** (the poll's `session/list` number, `hosted-session.ts:1333-1336`), and the relay writes it from **two** places — `pollJobs` (`:547-556`, `:569`) and the `readUse` path (`:585`). A shell-only frame-fed number in the same field would alternate with the poll's sum while a child runs: `ps` flaps between `1 background job(s) running` and `1 background sub-agent(s) running` (`relay-state.ts:237-241`) and `:191`'s idle test loses the meaning "jobs ≥ shells". The plan's old claim ("the count is right, `relay-state.ts` needs no change") was wrong. **Fix — one writer, chosen by who can report the list:**

- A new **`shellCounted` flag** in the relay's own closure: once a `jobs` **frame** has been seen for the session, the frame is the only writer of `jobs`; the poll's number is ignored until the session ends. A client on an older daemon sees no frames, so the poll (unchanged) stays its source — exactly the fallback the plan already intends. This is a relay-local fact, so `relay-state.ts` is still untouched.
- **The frame's `n` is `jobCount(rows)` — the running count of the daemon's full set, taken before any cap** (H1), so `n` is true, never client-bounded (the client keeps ≤ 32 of the rows, which is exactly why it must not compute `n` itself). `onJobs` therefore hands the relay the **count**, and the dock only the rows. Because `jobRows` never caps, `jobCount` and `jobRows(...).length` agree — the helper exists so the two cannot drift apart later.
- `local-runtime.ts`: the wrapper forwards `onJobs` beside `onSubagents` (`:576-581`) and the option types (`:243-244`); the listener's payload is `{ rows, count }` (rows = what the dock paints, count = the daemon's true running number).
- `relay.ts`: `const offJobs = session.onJobs?.((report) => { shellCounted = true; emit({ type: "jobs", n: report.count }); }) ?? (() => {});` beside `offAgents` (`:432-433`), cleaned up with the others (`:604-607`); `pollJobs` (`:547-556`) and the `emit({type:"jobs"})` in the `readUse` path (`:585`) both become no-ops while `shellCounted` — otherwise the two writers race by construction. `RELAY_JOBS_POLL_MS` (`:89`) is kept for the old-daemon case. Note the subscription is unconditional (not gated on `config.autoWake` like `offExit`, `:426-428`): a `ps` fact, not a wake decision.

**6. tui (pure modules first, then the component).**
This is where the panel appears; nothing computes in a `.tsx`.

- `background-list.ts` (pure): `jobLabel(id)` → `bg-3` ⇒ `sh-3` (any other id unchanged) — the mockup's id, while the wire keeps the real handle; the job row's `meta` keeps `running · 4m 10s` (`:394-404`); `jobDrawerView({ row, output, outcome, width, now })` → the drawer for a job: head rule `─ sh-3 · <command cut> ─── running · 4m 10s ─` (or `✓ exited (0)` / `✗ stopped` when frozen), a `… earlier output not shown` line when `truncated`, then the visible tail (≤ `JOB_TAIL_SHOWN = 12` lines, the child drawer's 8-label analogue), each line cut with `truncateCells`; `dockRows` (`:572-585`) accepts it so the viewport reserves its height (the Review-H3 lesson); `inputTitle` (`:588-599`) returns `null` for a job (see Owner questions Q1).
  **Blank rows (M3, the §6 Ink gotcha):** an empty `<Text>` measures `0×0`, so a real blank line in a job's output would collapse and the height `dockRows` reserved would no longer match what is painted — the frame shifts. Therefore `jobTailWindow`/`jobDrawerView` emit the string **`" "`** for an empty line (the output grid `trimEnd()`s it back to `""`), and the drawer has a **defined, non-zero height before the first read and for a job with no output yet**: a single dim `(no output yet)` row, never an empty body.

### Failure modes

| Case | How the state converges |
|---|---|
| A job exits while its drawer is open | The daemon's `onExit` ⇒ one `jobs` frame without the row ⇒ the client's list loses it ⇒ `reconcile` freezes the drawer with the outcome recorded from the same exit (`✓ exited (0)` / `✗ stopped`), the input is NOT re-routed (the child rule, `background-focus.ts:379-422`), and one final `job_output` read (the exit path of (h)) captures the last lines before the registry can be forgotten. The row leaves the list at once (Owner Q2). |
| A job printing fast | Nothing streams: the list frame is `{command, startedAt}`, identical bytes whatever the output rate. Reads are ≤ 1/s **only while open** (`refreshDue`), bounded by the request (`lines ≤ 200`, `maxChars ≤ 16 KiB`) and by the client (`boundJobOutput`). The read never moves `read()`'s cursor, so a chatty job cannot starve the model's `shell_output` (measured). A read that lands after the exit still answers (the registry keeps exited jobs until close). |
| Many jobs | One `jobs` frame per start/exit (no per-row deltas); the client keeps ≤ 32; the dock's 5-row window, `↑k ↓m` and `dockRows` are unchanged — `LIST_MAX_ROWS` already handles N items. 40 starts = 40 small frames, not a stream. |
| Binary / ANSI / control chars / a hostile pod | **The client is the gate** (a pod daemon's stripping would be UX only, §7): `boundJobOutput` caps the arrays before mapping, maps C0/C1 (incl. `ESC`, `\x9b`) to a space and strips the bidi/invisible format classes, 512 chars per line, and the same for `command`/`id`/`status`; the daemon only bounds sizes (`wireLine` ≤ 200 on the command, `jobOutput`'s lines/maxChars). Exec is **not** part of the contract — `JobTail` returns raw lines. So a `\x1b[2J` in a pod's stdout prints as text and cannot reach the terminal, and `‮` cannot reorder a line. The drawer cell-cuts each line (`truncateCells`), so a 100 KB single line cannot wrap the frame. |
| A job that only writes `\r` progress, or one huge line with no `\n` (M1) | `tail` splits on `\n`, keeps only the text after each line's last `\r` (a progress bar collapses to its latest frame), and drops the head partial line **only when a complete line remains** — otherwise it keeps that line's tail end and sets `truncated`. So the drawer shows a **non-empty cut line** while the job is visibly busy; it never opens empty. An output with no newline yet (nothing read at all) shows the defined `(no output yet)` row. |
| A blank line in the output (M3) | The tail/presenter emits `" "` for it, and the drawer body has a non-zero height before the first read — so `dockRows`' reservation equals what is painted and the frame does not shift (the §6 Ink `0×0` gotcha). Pinned by an F3 case. |
| A reload / attach | The list is full state, so a resync converges from any single frame; and it rides the snapshot's first page + the cut (`:1466,:1506`), so an attach that takes a snapshot has it even if the ring was evicted. `history_replaced` carries it (`:2594`) ⇒ `/clear` (which keeps jobs) does not lose it. |
| Two TUIs | Both get the same `jobs` frames; each drawer reads independently through a cursor-free RPC, so neither affects the other or the model. A kill from either removes the row for both within one frame. |
| `/clear` | Jobs survive (`clear-keeps-jobs`); the barrier's cut carries `lastJobs`, the App resets only its own drafts/dock (`resetDock`, `App.tsx:1956`) and re-receives the list from the same session's next frame or the resync. |
| Quit | The refresh timer is cleared on unmount; no read is issued after it. The job itself keeps running daemon-side (or dies with `session/close` on a confirmed `/quit` of a detached run) — the confirm now counts it (Q3). The kills `close()` performs (`hosted-session.ts:2692`) are not framed: `publishJobs` returns at once when `closed`. |
| The relay / `ps` (9d) | **One writer (H1).** The first `jobs` frame sets `shellCounted`, after which the frame is the only writer of `model.jobs` and both old writers (the 30 s poll, and the `readUse` emit on the wait path) are silenced — so a start/exit corrects `ps` within one tick, and the count can never alternate with the poll's shells+children sum while a child runs (`ps` no longer flaps, `:191`'s idle test keeps its meaning). The `n` is the daemon's running count taken **before** the client's 32-row cap. A daemon that reports no list (older pod binary) leaves `shellCounted` false, so the poll is the source exactly as today — nothing regresses. |
| A job stopped from the dock (M6 — owner Q6) | `killJob` ⇒ `JobController.kill` ⇒ `finish` ⇒ the existing `onExit` ⇒ `background_exit{status:"killed"}` and `kickWake()` (`hosted-session.ts:622-632`), the same path a child's cancel takes (`:660` maps `cancelled` ⇒ `killed`). With auto-wake **on** (Q6 (a), recommended) the user's `x y` starts a turn in which the model sees "killed"; with it **off** the exit is queued as a note for the next turn. Either way the kill is **not** silent and **not** doubled: the frame removes the row, the exit frame freezes the drawer as `✗ stopped`, and the TUI dedupes the notice by job id (the existing rule). § Notes records the debt if the owner picks (b). |
| An older daemon (new client) | No `jobs` frames, `MethodNotFound` for both methods ⇒ typed refusals: the pill never counts shells, `x`/`y` on a job row is impossible (no job rows), a job drawer cannot open. The screen is exactly today's. |
| An older client (new daemon) | `jobs` is `display`: the client skips it once as `unsupported` (`updates.ts:408-416`); no `mandatory` flag ⇒ no failed turn. Nothing waits on a client. |
| Clock skew (pod vs laptop) | Elapsed is computed from the daemon's `startedAt` with the laptop's clock (the mockup's `4m 10s`). A skewed pod clock shows a skewed duration — the same, already-accepted behaviour as `SubagentRow.startedAt`. Never a fake 0: the row is only painted from a frame that carried `startedAt`. |
| A registry without `tail` (a fake, a foreign impl) | `job_output` answers `{found:false, reason}`; the drawer shows the reason as a notice and stays open. Never a throw at a UI. |
| Two publishes racing the cut | `publishJobs` is synchronous in the same tick as the emit, and `lastJobs` is written before it — so a snapshot taken by a re-entrant sink sees either the old list or the new one, never a torn one (the same rule `publishSubagents` uses, `:1260-1275`). |

## Owner questions

Each is behaviour the owner must decide; my recommendation first.

1. **With a shell job's drawer open, what does the input do?** (a) *Recommended:* it stays on the **main agent** and the input rule is a plain line (no `→ sh-N`): the drawer is read-only, so typing and Enter go where they always do. (b) The input is hidden/disabled while a job's drawer is open (nothing to send). — I recommend (a): it needs no new rule, and a hidden input reads as "the session is blocked".
2. **Does a job stay listed once it has exited?** (a) *Recommended:* no — it leaves at once, exactly like a child (`P5 (a)`), and the transcript's exit notice is the record; a frozen drawer stays readable until closed. (b) It stays greyed (`✓ exited`) for ~5 s, then leaves. — (a) keeps one rule for both kinds; (b) is easy to add later if you miss it.
3. **Does a running shell job count in the quit confirm, and which quit actually kills it?** (a) *Recommended:* yes, worded apart (`2 agents · 1 shell job will keep running`). The confirm must name **exactly** which quit closes the session and kills the jobs — only a **confirmed `/quit` of a detached run** (the TUI whose quit closes the session for every TUI on it, `docs/fix/detach-live.md` D1/Q7) or **the last TUI of a `--rm` run** (which deletes the workload after a confirmed save). A plain detach — closing the window, SIGHUP, a crash, a `q` that only detaches — **never** kills jobs (§7 pod/container lifecycle: it detaches and the workload and session stay), so the wording must not claim it does. (b) Agents only, as today. — (a) is the honest one; the wording is the only cost, and it must use the two conditions above, not "quitting" in general.
4. **The drawer's output: two labelled sections or one merged block?** (a) *Recommended:* stdout, then a `stderr` marker line and stderr — the two streams are already separate in the registry and interleaving them would invent an order that never existed. (b) Merged as the model's `shell_output` result does (`tools/src/background.ts:38-42`). — (a); the model's merge is for a different consumer.

Add a relay test: one shell plus one child running, poll = 2, frame = 1; `ps` must not flap, and the idle decision stays blocked.

- **M1. Output with no newline makes an empty drawer.** The design says "take the last `maxChars` of `buf`, drop a head partial line". A job that writes progress with `\r` (curl, docker build, npm, pip) or one long line with no `\n` has a single line in the window. Dropping the "head partial" then drops **everything**, and the drawer shows nothing while the job is visibly busy. "Strip `\r` before splitting" also merges the overwritten frames of a progress bar into one huge line. **Plan change:** in `StreamBuffer.tail`, split on `\n`; inside each line keep only the text after the last `\r` (a terminal overwrites it); drop the head partial line **only if at least one complete line remains**, otherwise keep its tail end marked `truncated`. Add exec test cases: `"10%\r50%\r90%"` ⇒ `["90%"]`; a 1 MB line with no newline ⇒ one non-empty, cut line plus `truncated`.

- **M2. The sanitising contract is spread across three places and aimed at the wrong boundary.** `JobTail.stdout` is documented as "already sanitized" (an exec-layer promise). Test 3 asserts the stripping at the **daemon**. Under §7 a pod daemon is untrusted, so daemon-side stripping is only UX; the **client** is the only real gate. The plan names no function for the output path ("C0/C1 stripped, ESC ⇒ space"). **Plan change:** (a) remove "already sanitized" from `JobTail`; exec returns raw lines and the daemon only bounds sizes. (b) Name the client gate. `boundJobOutput` maps each line through the `progressText` character class (`[\u0000-\u001f\u007f-\u009f]` ⇒ space, `client/mapping.ts:90-94`) but with its own 512-character cap, not `progressText`'s 200. Tab becomes one space, so cell measurement matches the terminal. Also strip the bidi and invisible format controls (`U+200B-U+200F`, `U+202A-U+202E`, `U+2066-U+2069`), which can visually reorder a line. `stdout`/`stderr` arrays are capped to ≤ 200 entries **before** mapping. The same applies to `command` in rows and in `JobOutputResult`. (c) Move the hostile-input assertions into **client** test 5: a fake daemon returns `\x1b[2J`, `\x9b31m`, `‮`, a 300-entry array and a 1 MB line, and the plain result contains no control or format character and stays within the bounds. Keep the daemon test for bounding only.

- **M3. Ink's blank-row gotcha (§6) will hit the drawer.** Real output has empty lines. An empty `<Text>` measures 0×0, so those rows collapse. Then the height `dockRows` reserved (Review-H3) no longer matches what is painted, and the frame shifts. **Plan change:** `jobTailWindow` / `jobDrawerView` emit `" "` for an empty line. The drawer also gets a defined state before the first read and for a job with no output yet (a single dim `(no output yet)` row) instead of an empty, zero-height body. Add a case to F3: a tail containing `""`, and the frame height still equals the terminal's rows.

- **M4. The F4 timer test is not yet deterministic.** "Drive a fake clock or count with `JOB_REFRESH_MS` shortened through an injected value" leaves the seam open. Real timers in an Ink frame test are either flaky or, with a lenient count, vacuous. **Plan change:** name ONE seam: an optional `jobRefreshMs` prop on the App (or an injected `schedule`), used only by tests. F4 then asserts an exact read count: 1 on open, +1 per tick, 0 after Esc, plus one final read when the exit frame is seen. It also asserts that the count stays at 0 while the dropdown is open but no job drawer is open. The ≤ 1/s rule must not depend on `refreshDue` alone if the App's effect can re-arm on every render. State that the interval is created once per open job target, keyed by the job's id.

- **M5. The blast metadata is understated.** The header says `Blast: cross-module · Suited: DeepSeek exec (standard Review; no §7 invariant changes shape)`. But the task adds protocol methods and a protocol update (§7 protocol), and it carries pod-supplied bytes to the terminal (§7 "a pod is not trusted" / "never write raw"). Under §10 that is `load-bearing`, which requires a fresh-context Review. The owner already required Opus to review this plan for exactly those reasons. **Plan change:** `Blast: load-bearing`, Review = mandatory fresh-context red-team of M2 and H1. Who executes stays the owner's call.

- **M6 (owner decision missing). A user's kill wakes the model.** `job_kill` ⇒ `finish` ⇒ `onExit` ⇒ `background_exit{status:"killed"}` ⇒ `kickWake()` (`hosted-session.ts:622-632`). With auto-wake on, the user's `x y` on a shell job starts a model turn that sees "killed". The plan never mentions this. Children behave the same way (`:660` maps a cancel to `killed`), so the behaviour is at least consistent, but it is a visible side effect of a new user action. **Plan change:** add **Q6**: "Does stopping a shell job from the dock wake the agent?" (a) Yes, as for a child today; the model learns its watcher is gone. (b) No: a user-initiated kill is marked, and that exit does not wake. Recommend (a) for consistency. Add a failure-mode row for it either way.

- **L1.** `jobRows` will carry `Job.startedAt = Date.now()` (`background.ts:52`), not the host's injected `now` that sub-agent rows use (`hosted-session.ts:636-638`). A daemon test cannot pin the elapsed time with it. Note this, or use only relative assertions.
- **L2.** Add an explicit §7 paragraph to Design §2/§3 recording the `job_kill` trust analysis above (laptop-originated, `x`+`y` confirm, acts on the pod's own registry only, no laptop effect, no lasting approval), so the Review can check the exact claim.
- **L3.** Test 3 "a 1 MB line ⇒ ≤ the char cap" should check the M1 rule (a non-empty cut line), not only the cap. Otherwise it passes when the line is dropped entirely.

**Owner questions 1–5:** well posed, and the recommendations are sound. Q3's wording should say *which* quit closes the session: only a confirmed `/quit` of a detached run, or the last TUI of a `--rm` run. A plain detach never kills jobs, so the confirm must not claim it does. Add Q6 (M6). Nothing else in the plan takes a decision away from the owner.

**Verdict: REVISE.** The design is sound and the load-bearing assumption holds. Apply H1 and M1–M6 to the plan text (none needs a redesign), then execute.
