# fix/ios-build-pushcore — the iOS archive fails: the Live Activity target cannot import `PushCore`

`Type: fix · Size: S · Blast: contained (native target config) · Suited: DeepSeek exec, Opus review`

## Context

*— claude-opus-5-5 (orchestrator), 2026-11-16*

`xcodebuild archive` (the owner's install build, `.tentacle/tmp/mobile-ota/build.sh`) fails since `feat/mobile-live-activity` merged:
`apps/mobile/targets/live-activity/LACore/LACore.swift:23:8: error: Unable to resolve module dependency: 'PushCore' (in target 'liveactivity')` → `** ARCHIVE FAILED **`.
Cause: `PushCore/*.swift` are plain sources of the Notification Service target (`targets/notification-service/PushCore/`); only the SwiftPM test package (`native-tests/PushCoreTests/Package.swift:18-22`, symlinked `Sources/PushCore`) makes `PushCore` a module, with `LACore` depending on it. In the Xcode project generated by `@bacons/apple-targets` there is no `PushCore` module, so `import PushCore` fails in the widget target. The SwiftPM tests pass, so nothing caught it.
**Proven workaround (orchestrator, build-only, not committed):** in `LACore.swift` guard the import with `#if canImport(PushCore) … #endif` AND compile the `PushCore` sources into the live-activity target too (copied the folder to `targets/live-activity/PushCore/`); the archive is being rebuilt with it.

## Implementation

*— claude-opus-5-5 (orchestrator), 2026-11-16*

- **Design:** (1) `LACore.swift`: `#if canImport(PushCore)` / `import PushCore` / `#endif` (SwiftPM keeps the module; Xcode compiles the same sources in-target). (2) the live-activity target compiles the PushCore sources (symlink or config, per the check). (3) No change to PushCore code.

- **Tests (red first):** extend `apps/mobile/test/app-config.test.ts`: the live-activity target includes the PushCore sources (the symlink exists and points to the NSE folder, or the config lists it) and `LACore.swift` guards the import with `canImport`. The native SwiftPM tests (`native-tests/PushCoreTests`) must still pass (`swift test` there if the toolchain is available; say so if not).

## Execution

*— deepseek-v4-pro (executor), 2026-11-16*

**The plan's load-bearing check, re-run — it is INAPPLICABLE as written, and the
mechanism it assumed is WRONG.** Two findings, both by execution, both in
`.tentacle/tmp/ios-build-pushcore/` (scratch copy of `apps/mobile`, prebuilt
there, never in the tree):

1. **The grep has nothing to find.** `@bacons/apple-targets` 5.0.0 does not
   enumerate files at prebuild time: it links each target folder as ONE
   `PBXFileSystemSynchronizedRootGroup` (`with-xcode-changes.js:341-378`,
   `path = "live-activity"`), so `project.pbxproj` contains no per-file entry.
   On the orchestrator's own prebuilt tree `grep -c PushPipeline.swift
   project.pbxproj` = **0** while the archive compiled all six PushCore files.
   So "grep for `PushPipeline.swift` under the liveactivity target" can neither
   confirm nor deny symlink-following.
2. **The fallback option does not exist.** `Config` in
   `@bacons/apple-targets/build/config.d.ts:64-112` has `type`, `name`,
   `bundleIdentifier`, `frameworks`, `entitlements`, `colors`, `images`,
   `exportJs` — **no source/folder option**. The plan's "use the target config's
   own source option to add `../notification-service/PushCore`" is therefore
   impossible with the installed version.
3. **A FOLDER symlink is NOT followed; PER-FILE symlinks ARE.** Decided
   empirically, by `xcodebuild -project ios/tentacle.xcodeproj -target
   liveactivity` in the scratch:

   | scratch state | result |
   |---|---|
   | current branch, nothing added | `LACore.swift:23:8: error: Unable to resolve module dependency: 'PushCore'` · `** BUILD FAILED **` |

   So the Design's "(2) the live-activity target compiles the PushCore sources
   (symlink or config, per the check)" resolves to **per-file symlinks** — the
   plan's own "ONE source of truth, never a copied folder" is kept, and the
   forbidden shape (the orchestrator's proven workaround, a copied folder) is
   avoided. `LACore.swift`'s guard is still needed for the SwiftPM module.
