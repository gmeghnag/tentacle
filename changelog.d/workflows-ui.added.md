- **Workflows: the project's catalogue, a start pinned to the file you saw, and one step's prompt and report on demand.** A new `session/workflow_catalogue` read lists the project's workflow files — each validated and hashed against that session's models and agent types, with whether its hash is approved — asking nothing and starting nothing. A start now carries the `hash` the caller saw, so a file edited in between is refused `changed` with nothing run, and every refusal carries a machine-readable `refusal` word (`changed` / `running` / `invalid` / `inputs` / `unavailable`) beside its text. The catalogue names the absolute folder it read, and, when that folder holds no workflow, where some were found higher up — a display-only hint that can never be loaded. A second new read, `session/workflow_step`, answers the resolved `prompt` and the `report` of a single step execution — the detail a run's live row deliberately does not carry — choosing the newest attempt by default or the `attempt`/`round` asked for, and saying "not available" (an empty answer) for a step that never ran or whose record a compaction has since dropped, rather than showing another step's text. A step still running answers as live, with its prompt and no report. The client reads it — and the catalogue, and a run's live list, and the start / stop / resume / re-run-step actions — through one bounded, sanitized seam per session (`@tentacle/client`'s `workflows` module), so a `serve` daemon's runs reach every attached terminal and phone; from a daemon this client does not trust to run workflows (a pod under `run`/`attach`) the list is dropped and every action refuses locally, sending nothing. In the TUI, a run in flight now shows as a rail above the input — a header with steps done and tokens against the budget, then one row per step with its glyph AND its word (`✓ ok`, `▸ running`, `? needs approval`…; a state this build does not know is shown as its own word), windowed to seven rows around the active step on a long graph, narrowing by dropping `[where]` then the model — taking its rows from the transcript so the input never moves, and leaving when the run ends. `/workflow` opens a two-column panel (the steps; the selected one's detail, with `o` to read its prompt and report and `r` to re-run it), and `/workflow run <name> [k=v …]`, `stop` and `resume` act on the session's run, every reply or refusal shown as a notice. At rest — no run in flight — the live area carries one line naming the project's workflows and what each needs (`? needs approval`, `✗ invalid`, `✓ approved`), narrowing with the terminal from names and words to glyphs to a count, and saying nothing at all in a project with no workflows; `/workflow` lists them above the runs with an invalid file's errors and its path, says whether git ignores the folder, and `run <name>` now pins the hash of the file the person saw, so a file edited since is refused `changed` instead of run as something else — a workflow whose required inputs were never given pre-fills the command instead of starting half-specified. The list is re-read when the session opens, when a turn ends, when a run ends, when an approval is answered and on `/workflow`, never by polling, and its one line takes its row from the transcript so the input never moves.
